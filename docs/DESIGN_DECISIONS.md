# 设计决策

这里记录几个关键设计为什么是现在这样、考虑过哪些替代方案，以及目前已知的不足。代码结构本身见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 1. 为什么是四个 Agent，而不是一个

### 演进过程

最早只有两个角色：攻略 Agent 负责提取地点，路线 Agent 负责其余全部工作，包括查交通酒店、排日程、推荐餐饮，以及判断自己的结果有没有问题。

实际使用中暴露出两类反复出现的错误：

1. **同一地点出现两次**：两篇攻略用不同名字（例如简称和全称）写了同一个景点，被排在了不同的日期。
2. **同一家餐厅重复推荐**：午餐和晚餐、或者连续两天推荐了同一家店。

排查后，我认为根因不在提示词写得不够细，而在结构上：

- 「自己写、自己检查」时，模型会沿着刚才的推理去确认结论，很难发现自己的问题。
- 一次调用同时承担查资源、排日程、自查，输入里混着攻略原文、车次、酒店和路线结果，输出 schema 也很大；任何一部分格式出错，整份结果都要重来，也无法只缓存没变的部分。
- 餐饮去重的集合在午餐循环和晚餐循环里各自重置（`dining.py`），这是代码 bug，但流程中没有一个独立环节能发现它。

### 拆分原则

拆分时考虑的不是「职责听起来不同」，而是以下三个问题：

| 问题 | 如果答案是「是」 |
|---|---|
| 这一步是否需要**不同的上下文**，甚至需要**刻意看不到**某些信息？ | 拆开 |
| 这一步是否需要**不同的工具权限**？ | 拆开 |
| 这一步的输出能否用一个**小而独立的 schema** 描述，并单独缓存、单独重试？ | 拆开 |

据此得到四个角色：

- **检验 Agent** 是拆分的主要动机。它在全新的上下文里只拿到需求、原始证据、查询记录和最终计划，**看不到行程 Agent 的推理过程**，以避免确认偏差。它没有任何工具，只能引用已有的 `evidence_id`。
- **资源 Agent** 只能调用飞猪，并且代码限制了查询范围（[resource.py](../backend/app/agents/resource.py)：城市必须在本次旅行内，门票查询必须对应行程中已有的活动）。它的任务是「从已查到的选项里选一个」，输出只有 `selected_id + reason`，出错代价很小。
- **行程 Agent** 只能调用高德的地点、路线、天气工具，负责分日、排序和时间线。
- **攻略 Agent** 只读攻略，负责整理区域分组和用户明确提出的必去/排除项。

### 考虑过但没有采用的拆分

- **交通、住宿、门票各一个 Agent**：三者使用同一个工具（飞猪 CLI），做的都是「在查到的选项里按条件挑一个」，拆开只会增加交接成本，所以合并为资源 Agent。
- **独立的餐饮 Agent**：餐厅推荐依赖当天时间线稳定之后各餐次附近的活动位置，与行程强耦合。真正的问题是去重，这在代码中统一处理（一张全程的门店占用表），不需要另一个模型。
- **需求理解 Agent**：只是一次没有工具的结构化抽取（`ChangeRequest` / `RequirementUpdate`），放在协调节点里调用即可。

### 这里「Agent」的确切含义

需要说明的是：四个 Agent **共享同一个模型配置和同一个 `AgentRuntime`**，它们不是各自独立运行、相互对话的进程。每个 Agent 是一组「指令 + 输入上下文 + 输出 schema + 工具白名单」，由 LangGraph 图按确定的顺序调度。

没有采用 Agent 之间自由对话的方式，是因为旅行规划有大量硬约束（日期、预算、必去项、营业时间），用户需要知道每一步为什么这样排。确定的编排流程更容易复现、调试，也更容易写测试；代价是灵活性较低，例如行程 Agent 不能直接让资源 Agent 重新查询，只能通过协调器转达。

## 2. 检验 Agent 和代码规则的边界

### 划分标准

> 能用确定性算法根据结构化数据判断的，交给代码；需要理解自然语言证据或做语义判断的，交给检验 Agent。代码拥有否决权，检验 Agent 只能增加问题，不能撤销代码发现的问题。

| 由代码判断 | 由检验 Agent 判断 |
|---|---|
| 日期是否完整覆盖、城市顺序是否正确 | 「北京路」和「北京路步行街」是否为同一个地方（POI ID 不同） |
| 地点 ID 是否在所选攻略的地点池中 | 攻略中「周一闭馆」是否适用于这一天、这个场馆 |
| 预算加总、费用口径（每人/每间/每晚） | 一天之内是否来回折返、强度是否过大 |
| 时间线重叠、营业窗口、最晚入场（数据已解析时） | 证据是否真的支持计划中的说法 |
| 规范化名称或 POI 去重 | 问题应归属哪个 Agent，属于可自动修复、需要补查证据，还是需要用户决定 |
| 锁定项、必去项是否保留 | |
| 报价是否过期、审查报告是否与当前计划匹配 | |

对应代码：`check()`（[nodes/review_loop.py](../backend/app/nodes/review_loop.py)）、`check_itinerary`（[rules.py](../backend/app/rules.py)）、`confirmation_blockers`（[decisions.py](../backend/app/decisions.py)）、`duplicate_issues`。

### 两者的结论如何合并（`Planner.audit`）

1. 代码规则先执行，产出 `issues`。
2. 检验 Agent 独立生成 `ReviewReport`。
3. 代码发现的每个阻断问题，如果报告中没有，就补充为 `code_constraint` finding。
4. 代码有阻断时，报告即使是 `pass`，也被强制改为 `revise` 或 `needs_evidence`。
5. 检验 Agent 调用失败时，状态是 `review_unavailable`，**绝不会被当作 pass**。

### 检验 Agent 自身的输出也要经过代码校验

模型审查同样会出错，所以报告本身也要验证（[reviewer.py](../backend/app/agents/reviewer.py)、[reviewing.py](../backend/app/reviewing.py)）：

- **结构**：必须正好覆盖 10 个检查维度；存在 blocker 时，状态不能是 pass（Pydantic validator）。
- **引用**：`evidence_ids` 必须存在于本次查询记录中，`field_path` 必须是计划中真实存在的 JSON Pointer，`dates` 必须属于这份计划。
- **语义**：与代码已经算好的事实矛盾的结论会被拒绝，例如把 16:40–17:40 判为超出 10:00–18:00 的营业时间。
- **算术**：衔接时间是否足够，用代码计算的 `available_minutes` 和 `route_minutes` 直接改正（`correct_transfer_arithmetic`）。

每一层只给模型一次纠正机会，仍不合格就放弃这份报告。

### 实践中学到的

早期让检验 Agent 自己比较时刻、计算时长，它经常出错：把「最晚入场 16:00」当成离场期限，或者把已经包含在路线耗时里的步行时间再加一次。每遇到一次，就在提示词里补一条规则，最终提示词变得很长（见下文「已知不足」）。

更好的做法是事后才逐步采用的：**把所有能计算的比较预先算好，作为事实放进审查输入**（`review_scope` 里的 `transfer_timing`、逐活动的开放窗口比较），检验 Agent 只负责解释这些事实，不负责计算。

## 3. interrupt 恢复时如何保证状态一致

可能出问题的场景有：用户在旧标签页回答了一道已经过期的问题；回答期间修改了需求；服务在节点执行到一半时崩溃；旧任务的模型调用在新任务开始后才返回。

### 问题与对应的机制

| 风险 | 机制 | 位置 |
|---|---|---|
| 两个请求同时修改同一个旅行 | 每个旅行一把 `asyncio.Lock`；数据库中 `start_run` 在 `BEGIN IMMEDIATE` 事务里检查 `version` 和是否已有 `running` 运行 | `Planner.gate`、`Store.start_run` |
| 页面基于旧数据提交 | 所有写请求带 `base_version` 和 `updated_at`，不一致返回 409 | `Planner.submit` |
| 回答的是旧问题 | interrupt 载荷中包含 `round_id = digest(问题, 历史回答, generation, draft_revision)`；恢复时 `round_id`、`draft_revision` 必须一致，回答必须恰好对应当前这一道题 | `decision_gate` |
| 等待回答期间修改了需求或攻略 | 恢复前比较 checkpoint 中的需求和所选攻略，一旦变化就拒绝恢复，必须开启新 thread 重新规划 | `submit` 中的 resume 分支 |
| 旧运行的模型/工具结果晚到 | 每次模型调用、工具调用前后都执行 `assert_current`：运行不再是当前运行时直接丢弃 | `AgentRuntime.assert_current` |
| 旧运行结束时覆盖文档 | `execute` 写文档前确认 `active_run` 仍是自己 | `Planner.execute` |
| 服务崩溃或被停止 | 检查点在 SQLite 中；取消时运行标为 `recoverable`，启动时把遗留的 `running` 也改为 `recoverable`；「继续本次任务」从最后一个检查点恢复 | `execute`、`Store` 初始化 |
| 本轮失败留下半成品 | 提交时保存 `round_backup`，失败后恢复上一轮候选，并标记为「需重新审查」 | `execute` 的异常分支 |

### LangGraph 的重放语义

LangGraph 恢复 interrupt 时，**会从头重新执行包含 `interrupt()` 的那个节点**，而不是从 `interrupt()` 那一行继续。因此：

- 所有 `*_gate` 节点在 `interrupt()` 之前只做纯计算（读取 state、计算 `round_id`），不调用模型、不查询外部接口、不写数据库。重新执行的结果与第一次相同，`round_id` 也就一致。
- 有副作用的操作（模型调用、外部查询）都放在其他节点中，它们的输出会写入检查点。
- 节点执行中途崩溃时，这个节点会整体重新执行。外部查询大多会命中缓存（`agent_results` 按语义参数缓存工具结果，适配器层也有缓存），但 `queries` 表可能多出重复记录。这张表只追加写入，用作证据日志，重复记录不影响正确性。

### 文档和检查点：哪个是真实状态

- **检查点**是工作流的真实状态，决定下一步执行哪个节点、state 中有什么。
- **`trips.document`** 是给前端展示的投影，在 `execute` 结束（进入等待、完成或失败）时由检查点内容写入。

两者之间存在一个短暂的不一致窗口：图已经运行到 interrupt，但文档还没写入时服务崩溃。这时运行状态是 `recoverable`，恢复时会从检查点重新得到正确状态，不会丢失数据，只是用户会多看到一次「继续任务」。

## 4. 其他决策

- **只用用户勾选的攻略作为地点来源**：自动搜索补充攻略会让来源不可控，用户也无法核对。缺少地点时，宁可少排、说明原因。
- **酒店只有用户明确采用后才参与日程**：如果让模型「暂选」一家酒店来算接驳，用户没有同意的假设就会进入日程和费用，审查也会据此要求补选酒店、阻止确认。现在未选择的酒店只出现在推荐列表中，不影响路线，也不阻止确认；`selected_by_user` 只能由用户操作设置。
- **一次只生成一条候选**：早期的 schema 允许生成三条候选，但后续只使用第一条，多出的输出没有意义。现在是一条候选加局部修改。
- **模型只返回 JSON，并经过 Pydantic 校验**：失败时把具体的字段错误返回给模型重试一次，再失败就报错，不对输出做猜测性修补。
- **SQLite + 进程内任务**：项目是本机单用户工具，不需要消息队列或独立的 worker。代价是无法水平扩展，这在当前场景下可以接受。
- **往返交通可以交给用户**：出发地往返的班次多数用户会自己定，而系统选错班次（夜车、到得太晚、走得太早）会让首末两天整天作废，并引出一连串只有用户才能回答的追问。勾选「往返交通自行安排」后，只规划目的地内的行程和多个目的地之间的交通，往返段不查询、不校验、不追问。
- **只问回答能改变的事**：用户的回答只能修改偏好、预算、交通方式、步行上限、时间限制、住宿区域、重复授权和必去/排除景点。选酒店要在住宿面板操作，某天的出发地址、往返班次也无法通过回答记录，这些都不作为追问，而是写成资料缺口。同一道问题回答两次仍未解决就不再问，保留草稿并带着阻断项进入确认，避免反复追问同一个问题。
- **车站、机场不猜航站楼**：高德对「白云国际机场」会返回主楼、各航站楼、停车场等多个 POI。名称唯一匹配或班次给出的航站楼唯一匹配时直接定位；否则问用户选哪个航站楼或进出站口，不替用户猜。

## 5. 消融评测：每个设计值不值

拆分理由（第 1 节）和代码/Agent 的边界（第 2 节）都是设计时的判断，需要用数据验证。做法是逐个关掉一项设计，在同一批需求、同一份外部数据上比较结果（[backend/eval/](../backend/eval/README.md)，开关在 [app/ablation.py](../backend/app/ablation.py)）。

- **固定外部数据**：高德、飞猪返回录制后回放，排除接口数据随时间变化的影响。
- **判分不依赖被测设计**：判分时临时恢复全部设计，按完整规则检查；地点重复用独立实现的规则（高德 POI ID、去后缀名称、用例中列出的已知别名）判断，不复用被关掉的去重代码，避免「关掉检测就测不出问题」。
- **漏检口径**：系统判为可确认（审查通过且无阻断）的方案里仍存在的违反。

DeepSeek 与 GPT-5.6 Luna 两个模型 × 5 条需求 × 每组 1 次的结果：

| 组别 | 关掉的设计 | 含违反的方案 | 违反处数 |
|---|---|---|---|
| 完整系统 | 无 | **0 / 10** | 0 |
| `no_reviewer` | 检验 Agent（报告固定为通过，代码规则仍可否决） | 3 / 10 | 4 |
| `no_dedupe` | 跨攻略的统一地点身份、全程地点与餐厅去重 | **8 / 10** | 12 |
| `no_code_checks` | 代码硬约束校验（日期、时间线、预算、营业窗口、重复等） | 1 / 10 | 1 |

结论与第 2 节的划分一致：

1. **可计算的判断必须由代码负责**。关掉全程去重后 8/10 份方案出现重复（主要是同一家餐厅午晚餐连推），而这一组检验 Agent 一直开着，没有发现任何一处。模型审查替代不了确定性规则。
2. **检验 Agent 的价值在语义判断**。关掉它后出现的都是「陈家祠 / 陈氏书院」这类高德 POI 不同、代码无法合并的别名重复；代价是模型调用约翻倍。
3. **代码硬约束校验在这批用例中几乎没有体现差异**，因为时间线本身由确定性代码生成。它的作用是兜底，不应据此删除。

评测本身也有价值：试跑中暴露的往返班次选择、航站楼定位、午餐规则、追问兜圈等问题都在真实使用中存在，修复后才进入正式评测。


## 已知不足

下面这些问题我清楚存在，但还没有处理：

1. **修复循环不在图上**。真正的审查-修复循环是 `assess_result()`（[nodes/review_loop.py](../backend/app/nodes/review_loop.py)）里的 `while True`，它直接调用 `repair()`。这样做是因为循环需要 `backup`、`no_progress`、`diagnosed` 等局部变量，放进图里就要把它们都加入 `TripState`。代价是从图上看不到这个循环，修复轮次也没有单独的检查点。更好的做法是把循环变量放进 state，用条件边表达循环。（图上原有一条恒不触发的 `check → repair` 边，已删除。）

2. **检验 Agent 的提示词太长**（约 70 行），其中很多是针对具体误判打的补丁，例如关于「北京路」、「16:40–17:40」的规则。这说明仍有不少本该由代码计算的判断留给了模型。方向是继续把可计算的比较移进 `review_scope`，让提示词只描述原则。

3. **`TripState` 是一个约 50 个字段的宽松 `TypedDict`**，很多字段是任意 dict，没有 reducer。节点之间的依赖关系靠约定维持，新增字段时容易遗漏清理（例如 `revise_candidate` 需要手动重置 `repair_round`、`keep_current_plan` 等）。

4. **只在 Windows 上运行**：服务锁使用 `msvcrt`，飞猪 CLI 通过 Windows 下的 Node 入口调用。

5. **评测样本量小**：消融评测（第 5 节）只有 2 个模型 × 5 条需求 × 每组 1 次，结论只能说明趋势；代码硬约束校验在这批用例中几乎没有触发，作用尚未量化。另外判分只能发现「重复、超时、闭馆」这类可计算的违反，无法衡量路线是否合理、强度是否合适，也没有统计检验 Agent 的误报率。下一步是扩大到全部 25 条用例并增加重复次数，再补一批注入已知错误的行程来统计检出率与误报率。
