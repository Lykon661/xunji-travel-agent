# 消融实验

回答「为什么拆成四个 Agent、检验 Agent 值不值」：在同一批需求、同一份外部数据下，逐个关掉一项设计，看自动判分的违反数怎么变化。

## 组别

| 组别 | 关掉了什么 | 代码位置 |
|---|---|---|
| `full` | 无 | — |
| `no_reviewer` | 不调用检验 Agent，报告固定为 pass；代码规则仍有否决权 | `nodes/review_loop.py` `audit` |
| `no_dedupe` | 跨攻略的统一地点身份（广州塔=小蛮腰）、候选重复合并、全程餐厅占用表 | `places.py`、`dining.py`、`rules.merge_candidate_duplicates` |
| `no_code_checks` | 代码硬约束：日期覆盖、城市顺序、必去/排除、时间线、预算、营业窗口、重复等，只靠行程 Agent 和检验 Agent 自己发现 | `rules.py`、`decisions.confirmation_blockers`、`review_loop.check`、`candidates.discover` |

开关在 [app/ablation.py](../app/ablation.py)，默认全部不生效；也可以组合，例如 `no_reviewer+no_dedupe`。

## 怎么跑

在 `backend` 目录下运行，**先停止本机服务**（避免争用模型和高德配额）：

```bash
.venv/Scripts/python.exe -m eval.run_ablation --mode auto --out eval/runs/main
```

默认只跑**核心集**：5 条用例（`stress-gz-4d`、`stress-xa-4d` 地点池紧张，`gz-2d` 别名重复，`xa-3d` 周一闭馆，`bj-3d` 攻略天数多于行程）× 4 组 × 1 次 = 20 次，单次约 2～6 分钟，整体约 1～2 小时。需要第二轮时用同一个 `--out` 加 `--repeats 2`。

- 第一次跑到某个用例时，高德和飞猪的真实返回会录制到 `eval/cassettes/`，之后各组复用同一份数据。
- 想跑全部 26 条用 `--suite all`；只跑偏好条件约束用例用 `--suite constraints`；已完成的组合续跑时会跳过。
- 也可以按组分批：`--variants full,no_dedupe` 先跑去重对比，再跑 `--variants no_reviewer,no_code_checks`（同一个 `--out`）。

- `auto`：命中录制就回放，没命中（关掉某项设计后查了新地点）才实时查询并补录。汇总末尾会给出实时查询次数。
- `replay`：完全离线，没命中按查询失败处理。各组外部数据严格一致，但关掉设计后新出现的地点会缺少数据。
- 中断后用同一个 `--out` 重跑，已完成的组合会被跳过。
- 只跑部分用例：`--only gz-2d,cd-3d`；只重新生成汇总：`--report eval/runs/main`。
- 不要用 `--mode record`：它会覆盖已有录制。
- 连续两次因模型额度或登录失败，脚本会自动停止，这类运行不写入结果；恢复后用同一个 `--out` 续跑即可补上。

所有用例都开启了「往返交通自行安排」（`self_arranged_round_trip=true`）：出发地往返的班次由用户自己定，评测只看目的地内的行程规划，以及多个目的地之间的交通。这一项在需求表里也可以勾选。

运行时会自动回答规划中的追问（地点澄清选第一个候选，其余采用系统推荐），每组策略相同。超过 `--max-decisions`（默认 8）次就停下，按当时的候选判分。

## 输出

`eval/runs/<目录>/` 下：

- `summary.md`：可以直接贴进文档的对比表；`summary.json` 是同样的数据。
- `results.jsonl` / `results.csv`：每次运行一行，包含全部指标、结果、错误、模型调用次数和用时。
- `plans/`：每次运行的最终候选方案，用来人工抽查判分是否合理。

## 判分（[metrics.py](metrics.py)）

全部由代码判定。判分时临时恢复全部设计，所以关掉某项设计的运行，依然按完整规则检查。

| 指标 | 判定方式 |
|---|---|
| 日期覆盖错误 / 城市顺序错误 | 方案日期与需求起止日期逐日比对；城市压缩后与需求顺序比对 |
| 重复安排地点 | 高德 POI ID 相同，或名称去掉括号和「步行街/景区」等后缀后相同，即视为同一地点。这部分是独立实现的，不复用被消融的去重代码 |
| 重复推荐餐厅 | 高德 POI ID 相同（分店 POI 不同不算重复） |
| 无来源地点 | 景点 ID 不在所选攻略提取的地点池里，或没有原文证据 |
| 时间线冲突 | 同一天内活动时间缺失、结束早于开始，或与上一项重叠 |
| 营业/闭馆冲突 | 按高德返回的营业时间，闭馆日安排、超出开放窗口，或晚于最晚入场时间 |
| 未留午餐 / 步行超限 / 超预算 | 用完整的 `check_itinerary` 重新计算 |
| 漏检违反 | 系统判为「可确认」（审查通过且没有阻断）的方案里仍存在的违反 |
| 检验 Agent 额外阻断 | 检验 Agent 提出、但代码规则没发现的阻断数 |
| 违反用户条件 | 用户在偏好里写明的硬性条件没被满足：地点先后顺序、预约时刻、最少游玩时长、只用公共交通、公交查不到仍保留的景点（`rules.constraint_issues`）。给了距离的「少走路」计入步行超限；没给距离的只是目标，不计入 |
| 偏好条件抽取 | 用例 `expected_constraints` 列出偏好原文中应抽取的条件；统计应抽取数、实际从表单抽取数和种类正确数。地点 ID 运行时才生成，所以只比对种类 |

测试需求在 [cases.json](cases.json) 里。每条用 1～2 篇合成攻略，故意放了别名重复（广州塔/小蛮腰、陈家祠/陈氏书院、北京路/北京路步行街）、两篇攻略推荐同一家餐厅、攻略天数多于行程天数、周一闭馆、预算偏紧、城市顺序和攻略顺序相反等情况，`traps` 字段写明了每条的设计意图。

其中 5 条 `stress-*` 是地点池紧张的压力用例：行程 4～5 天，两篇攻略用不同名字写同一批约 6 个地点（如广州塔/小蛮腰、大雁塔/大慈恩寺），偏好要求「每天至少三个景点」，并让同一家餐厅靠近多天的景点。`gz-2d-constraints` 复用 `gz-2d` 的攻略，偏好里写了先后顺序、游玩时长、预约时刻和少走路四个条件，用来检查条件抽取和执行（套件 `constraints`）。其余 20 条地点充足，模型很少需要重复安排，去重组的差异主要靠这 5 条体现，分析时建议把它们单独列出来。可以用 `--only stress-gz-4d,stress-hz-4d,stress-cd-4d,stress-xa-4d,stress-bj-5d` 单独跑。日期是 2026 年 12 月的固定日期，过期后要整体平移日期再重新录制。

## 注意

- `no_code_checks` 为了避免后续节点崩溃，仍会丢掉不存在的地点 ID。所以「编造地点」在这一组里不会体现为「无来源地点」。
- 判分用的是运行结束时的需求。自动回答追问时如果放宽了步行上限，这部分不再计为违反；每次追问的内容都在 `plans/*.json` 的 `decision_history` 里。
- 模型输出有随机性。汇总里给出了每轮违反合计的「均值±标准差」，写结论时把样本量一起写上，例如「5 条需求 × 1 次」。样本很少时只能说明趋势，不宜写成百分比结论。
